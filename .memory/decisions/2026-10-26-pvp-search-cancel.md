# Decisions: 비동기 PvP 상대 검색 취소

- Date: 2026-10-26
- Status: Confirmed
- Scope: 비동기 PvP 상대 검색의 취소, 검색 상태 복구, 발급 티켓 취소와 경기 시작 경계를 설계한다. 이 문서 작성에서는 게임 코드, 데이터베이스, Azure 리소스를 변경하지 않는다.

## D01. PvP 방식과 작업 범위
- **Chosen**: 현재처럼 서버에 저장된 플레이어 캐릭터·장비 스냅샷을 랭킹 기준으로 검색하는 비동기 PvP를 유지한다. 동시 접속 상대를 찾는 실시간 매칭은 범위 밖이다.
- **Rationale**: 상대는 검색 대기 중인 플레이어가 아니라 이미 등록된 스냅샷이다. 취소 경합은 상대 응답과의 경합이 아니라 검색 취소, 티켓 발급, 경기 시작 사이에서 처리해야 한다.
- **Out of scope**: 이번 작업에서 레이팅 규칙, 스냅샷 갱신 방식, 전투 재생·판정, 매칭 범위와 대기 시간은 바꾸지 않는다.

## D02. 검색 ID와 중복 시작 요청
- **Chosen**: 클라이언트가 새 검색마다 UUID를 생성한다. 검색 시작, 취소, 상태 확인과 네트워크 재시도는 동일한 검색 ID를 사용한다.
- **Chosen**: 서버는 계정에 검색 ID를 연결해 저장하고 같은 ID의 시작 요청을 멱등 처리한다. 이미 검색 중이면 현재 상태를 반환하고, 티켓이 이미 발급됐다면 같은 티켓을 반환한다. 같은 ID로 두 번째 매칭 루프를 시작하지 않는다.
- **Rationale**: 검색 시작 HTTP 응답이 유실되어도 클라이언트가 같은 요청을 재시도해 중복 티켓이나 검색 작업을 만들지 않게 한다.

## D03. 취소 가능한 경계와 트랜잭션 경합
- **Chosen**: 검색 중 취소를 허용한다. 티켓이 `issued`로 발급된 뒤에도 `PvpScene` 시작이 서버에 확정되기 전까지 취소를 허용한다.
- **Chosen**: `PvpScene` 진입 시 시작 확인 API를 호출한다. 검색 취소와 경기 시작은 DB 트랜잭션으로 경합 처리하며 먼저 커밋된 동작이 이긴다.
- **Chosen**: 티켓 발급 후 시작 확인 전에 취소가 커밋되면 매치 기록을 `expired` 처리해 상대 스냅샷을 다시 매칭 후보로 풀고 결과를 레이팅에 반영하지 않는다. 시작이 먼저 커밋되면 취소를 거부하고 경기를 진행한다. 시작된 티켓은 취소하지 않는다.
- **Rationale**: DB에 기록된 순서가 기준이 되므로 화면 전환과 네트워크 응답의 도착 순서가 엇갈려도 발급·취소·시작 결과가 모순되지 않는다.

## D04. 취소 응답과 클라이언트 UX
- **Chosen**: 취소를 누르면 서버에서 취소 상태가 확정될 때까지 검색 창을 유지하고 취소 확인 중임을 보여준다. 확인 전에는 새 검색을 시작하지 않는다.
- **Chosen**: 연결이 끊겨 취소 응답을 받지 못하면 같은 검색 ID로 상태를 다시 확인하거나 취소를 재시도한다. 서버 상태가 확인될 때까지 재검색을 막는다.
- **Rationale**: 서버가 티켓을 먼저 발급했는지 클라이언트가 알 수 없는 상태에서 새 검색을 열면 이전 검색과 새 검색이 함께 진행될 수 있다.

## D05. 서버 검색 간격과 브라우저 이탈
- **Chosen**: 서버는 검색 상태를 최대 5초 간격으로 확인하고, 기존 검색 최대 대기 시간 60초를 유지한다.
- **Chosen**: 검색 ID는 브라우저 메모리에만 둔다. 새로고침이나 브라우저 종료 뒤 검색 상태를 복구하지 않는다. 페이지를 떠나도 서버 검색은 기존 제한 시간 안에서 종료된다.
- **Chosen**: 이탈 후 상대가 발견되어 발급된 티켓은 기존 10분 만료 정책을 따른다. 전투 시작·결과 제출이 없으면 레이팅은 변경되지 않는다.
- **Rationale**: 서버가 최대 5초 안에 취소를 감지하도록 하되, 브라우저를 다시 열었을 때 지난 검색을 자동으로 이어가지는 않는다.

## D06. 검색 상태 보존과 물리 삭제
- **Chosen**: 종료된 검색 상태는 10분 뒤 논리적으로 만료한다. 기존 일일 정리 작업에서 실제 행을 삭제하므로 물리 데이터는 만료 후 최대 약 24시간 더 남을 수 있다.
- **Chosen**: 검색 기록 삭제를 기존 일일 정리 작업에 추가한다. 정리 주기를 더 자주 바꾸지는 않는다.
- **Rationale**: 짧은 네트워크 재시도에 필요한 상태를 제공하면서 별도 상시 정리 작업을 추가하지 않는다. 검색량이 커져 기존 정리 배치 한도와 경쟁하면 계획 단계에서 배치 할당을 조정한다.

## 자동 확인된 코드 제약
- `TownScene.startPvp()`는 검색 오버레이를 띄우고 `pvpClient.findMatch()`가 끝날 때까지 기다린다. 현재 검색 오버레이에는 취소 버튼이 없다.
- `pvpClient.findMatch()`는 `POST /pvp/matches/search`에 빈 `{}`를 보내고, 상태 확인·검색 ID·취소 API는 아직 없다.
- `api/src/services/matchmakingService.js`는 저장된 스냅샷 후보를 찾으며 초기 ±100점에서 5초마다 범위를 넓혀 최대 ±500점까지, 최대 60초 검색한다.
- `MATCH_TTL_MS`는 10분이고 전투 시간은 60초다. `PvpMatches` 행은 상대를 찾았을 때 생성되며 현재 상태 제약은 `issued`, `completed`, `expired`, `rejected`다. 현재 `issued` 매치는 상대 스냅샷을 새 매칭 후보에서 제외한다.
- `PvpScene.create()`는 티켓을 검증하고 전투 시뮬레이션을 시작하지만, 현재 서버 시작 확인 요청은 없다. 매치 조회는 트랜잭션에서 `UPDLOCK, HOLDLOCK` 잠금을 사용하는 기존 패턴이 있다.
- `api/src/functions/pvpRetentionCleanup.js`의 정리 작업은 매일 03:15 UTC에 실행된다. 정리 서비스의 최대 10개 × 500행 배치 한도는 현재 정리 항목들이 공유하므로, 검색 기록을 추가할 때 다른 작업이 굶지 않도록 배분을 검토해야 한다.
- 현재 코드 흐름은 HTTP 연결 종료를 검색 중단 신호로 사용하지 않는다. 따라서 연결 종료에 기대지 않고 DB의 취소 상태를 주기적으로 확인한다.

## 이번 인터뷰에서 선택하지 않은 후보
- 전투·결과·레벨업 버튼의 키보드 조작과 전투 이동 키 통일은 사용자가 이번 작업에서 제외했다.
- 전투 터치 조작 안내와 가로 모바일 화면의 가독성 개선도 이번 작업에서 제외했다.

## 구현 계획에서 지킬 불변 조건
- 한 계정의 동일 검색 ID는 단일 검색 상태와 최대 하나의 발급 티켓만 가리킨다.
- 취소가 시작 확인보다 먼저 커밋되면 경기는 시작되지 않고 레이팅도 바뀌지 않는다.
- 시작 확인이 취소보다 먼저 커밋되면 취소할 수 없고 결과는 기존 서버 재생 검증 흐름으로 제출한다.
- 검색이 취소되거나 티켓이 만료되면 상대 스냅샷을 다시 검색 후보로 사용할 수 있어야 한다.
- 브라우저 메모리에서 검색 ID를 잃어도 서버 검색은 제한 시간·티켓 만료로 유한하게 끝난다.

이 결정은 다음 `/memory-plan`에서 상세 API 응답, 검색 상태 테이블과 스키마 변경, 만료 정리 배분, 검증 항목으로 나눈다. 이 문서 작성 단계에서는 구현·테스트·커밋을 하지 않았다.
